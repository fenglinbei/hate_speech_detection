## 根因记录

- 右栏依赖未命名的 CSS Grid 自动排位；请求错误区显隐或 DOM 顺序变化后，操作区可能落入可伸缩行，导致按钮被纵向拉伸。
- 页面、决策编辑器和原因列表同时设置纵向 `overflow`，形成嵌套滚动；右栏 `sticky` 高度与页面级滚动又产生第二条主滚动条。
- 移动端操作区固定在视口底部，详情编辑器依靠额外 bottom padding 避让，造成短屏和软键盘场景下的遮挡与留白。
- 原选区入口只创建默认 A mention，无法在高频重复表达场景中直接表达 A/B/C 去向。
- Case 导航分别依赖全量摘要下标或临时过滤结果，没有唯一的“当前可见队列”，因此搜索、筛选、上一/下一和确认后继续可能出现顺序不一致。
- 左栏重绘没有区分“保留用户手动滚动”和“业务事件后重新定位”，连续标注后当前高亮 Case 可能移出可视区。

- 右栏已经改为命名 Grid 区域；操作栏位于编辑区上方，桌面/平板只有详情编辑器承担主滚动，移动端操作栏改为决策区内粘顶。
- 选区栏已经提供 A/B/C 三个快捷入口，1/2/3 使用集中式 route 映射；阶段 B 的数字动作快捷键及按钮数字前缀已经移除。
- 客户端已经实现搜索模式循环、300ms 输入防抖、请求取消/序号保护、安全摘要高亮和最多五个 Case 的缓存。
- 服务端已经实现 `wp3-s21-review-search/v1` 搜索投影、三种模式、80 字限制、最多 424 项轻量结果及盲化字段约束。
- 左栏、Case 按钮、`[`/`]`、确认后继续和预取已经统一使用可见 Case 队列；普通重绘保留滚动位置，业务事件可触发当前项重新定位。

### 发布 blocker 修复与复核

在扩大端到端覆盖后发现并修复了三个发布 blocker：

1. **搜索竞态**：旧搜索触发的延迟 Case 加载可能在新查询完成后覆盖当前页面。搜索 generation 现在贯穿结果应用和 Case 加载，AbortController 之外再以序号阻止过期异步结果提交。新增延迟响应场景确认旧结果不会替换较新的空搜索结果或活动 Case；该场景已通过五视口 Playwright。
2. **确认期间仍可编辑**：确认请求在途时继续输入或导航，可能在确认写入后追加一份草稿。现在以 `confirmBusy` 锁定编辑器、原文、选区、提案条、搜索、筛选和导航，并取消待执行搜索；确认完成后才恢复交互。新增慢确认场景确认只产生一次 confirm 写入，不会排入 post-confirm draft；该场景已通过五视口 Playwright。
3. **短原文摘要泄露**：当冻结原文本身短于摘要上限时，搜索 `snippet` 曾可能等于完整原文。正文命中现在强制省略，必要时裁掉至少一个 code point；极短内容也不能用摘要替代单 Case 投影。服务测试已经加入“短原文/整段命中仍不返回全文”的断言，并随最终 Python 合并回归通过。

## 最终交互约定

### 1. A/B/C 快捷标注

- 阶段 A 和 raw-repair 模式完成有效选区后，显示三个等宽入口：
  - `1 · A 稳定核心`：创建 `A_candidate + stable_core_candidate`。
  - `2 · B 需上下文`：创建 `B_candidate + context_required`。
  - `3 · C 待核实`：创建 `C_candidate + evidence_required`。
- 点击或按数字键只创建 mention 并打开右侧详情，不自动确认 Case。
- “手动添加”仍以 A 为默认值；阶段 B 的 trim/expand/split 继续使用原有单一选区按钮。
- Case 已锁定、没有有效选区、焦点位于输入控件或有对话框打开时，1/2/3 不执行。
- 阶段 B 取消 1–6 动作快捷键和按钮数字前缀；六种诊断动作仍可点击。

最终快捷键为：

| 快捷键 | 行为 |
| --- | --- |
| `1` / `2` / `3` | 阶段 A 使用当前选区创建 A/B/C mention |
| `J` / `K` | 阶段 B 上一/下一提案 |
| `[` / `]` | 当前可见队列的上一/下一 Case |
| `Ctrl/Command + S` | 保存草稿 |
| `Ctrl/Command + Enter` | 确认并继续 |
| `?` | 打开快捷键帮助 |

### 2. 操作区和滚动层级

- 右栏固定为 `标题 → 操作区 → 请求错误 → 可滚动编辑区`，各区域使用明确的 Grid 名称。
- 桌面和平板工作台限制在 `100dvh`；页面本身不纵向滚动，中央内容与右侧编辑区分别滚动。
- 桌面右栏只有详情编辑区一个主滚动容器；原因列表随详情滚动，不再形成第二条滚动条。
- “保存草稿 / 确认并继续”保持正常按钮高度并固定在右栏顶部。
- 手机保持单页滚动；操作区位于决策标题下，进入决策区后才粘在全局顶栏下方，不覆盖原文选区。
- 删除原移动端底部固定栏及其占位；Mention 备注与删除按钮分区显示，并用间距和分隔线隔开。

### 3. 冻结原文搜索

- 同一个搜索框匹配 Case ID、别名和冻结原文，查询最大 80 个字符，所有输入均按普通文本处理，不支持正则。
- 搜索输入约 300ms 防抖；显示“搜索中 / N 条结果 / 无匹配结果 / 搜索失败”。
- 搜索模式使用单按钮循环，不使用下拉菜单。固定顺序是：

  `连续 → 多词 → 模糊 → 连续`

- 按钮显示当前模式（例如 `连续 ↻`），`title` 告知下一模式；点击后保留查询词、立即取消旧请求并重新搜索。
- 默认模式是“连续”，刷新恢复默认，不写入 localStorage。

三种模式的权威语义：

| UI | API `mode` | 规则 | 排序 |
| --- | --- | --- | --- |
| 连续 | `literal` | Case ID、别名或冻结原文包含连续查询文本；英文不区分大小写 | 冻结 frame 原序 |
| 多词 | `all_terms` | 按 Unicode 空白拆分、去重；每个词都必须命中 ID、别名或原文，词可分布在不同字段 | 冻结 frame 原序 |
| 模糊 | `fuzzy` | ID/别名先做连续包含；原文做本地有界编辑距离；查询少于 3 字时退化为连续 | 归一化距离，其次 frame 原序 |

模糊模式最大编辑数：

`min(4, max(1, floor(查询长度 × 0.2)))`

服务端提供 `GET /api/cases/search?q=<query>&mode=literal|all_terms|fuzzy`。响应 schema 为 `wp3-s21-review-search/v1`，每项只含 `case_id`、`matched_field`、短 `snippet`、命中位置和 `distance`。客户端使用 `AbortController` 与请求序号共同阻止旧响应覆盖新结果。

查询非空时，左栏 Case 项展示最多两行摘要，并用安全 DOM 节点和 `<mark>` 标出连续、多词或最佳模糊窗口；不得拼接未经转义的 HTML。

### 4. 统一可见 Case 队列

- `visibleCaseQueue` 是唯一导航真值，由“搜索结果顺序 + 全部/待确认/已确认筛选”合成，活跃项以 `case_id` 标识。
- 左栏、页面上一/下一、`[`/`]`、确认后继续和下一 Case 预取都使用该队列。
- 有搜索或筛选时显示 `结果 x / n · 全部 y / 424 · Case ID`；无条件时保持简洁位置文案。
- 查询、模式或筛选更新后：
  - 当前 Case 仍在队列：保留当前项并在左栏居中定位。
  - 当前 Case 被排除但存在结果：先 flush 有效草稿，再进入首条结果。
  - 草稿无效或保存失败：阻止跳转并保留当前项。
  - 无结果：保留主页面，禁用上一/下一并显示空状态。
- 普通列表重绘保留用户手动设置的 `scrollTop`；搜索/筛选更新、成功导航或成功保存后，才对当前项执行一次 `scrollIntoView({block: "center", behavior: "auto"})`。
- 待确认筛选中确认当前 Case 后，按保存前队列位置进入其后的下一条；搜索结果全部完成时保留条件并提示“当前结果已全部确认”，不跳回全量列表。
- 阶段 B 优先进入当前 Case 的下一未确认提案，Case 完成后才进入可见队列下一条。
