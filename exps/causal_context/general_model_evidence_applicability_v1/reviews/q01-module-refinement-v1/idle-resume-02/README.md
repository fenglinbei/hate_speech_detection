# Q01 模块实验：15分钟空闲检查与完整续跑

2026-09-16。用户授权“15分钟一次的GPU空闲检查，空闲后即开始GPU运行”，并明确确认“空闲后运行至完成，无固定截止时间”。这是一份独立的调度与入口修订，科学冻结、评分代码、所有已封存记录和1,711条部分检查点保持原状。

监控四张原物理卡0/1/2/3。启动即检查，此后每900秒检查一次，按首个检查时间的固定网格推进。四卡均通过原空闲门槛且UUID与原分配相同后，调用未修改的 `q01_module_execution.execute`，先续接剩余工程遍次，全部通过后进入科学六遍；不重复已完成请求。不设新的截止时间，运行到完成后释放GPU并自动进行原分析CLI的CPU检查与分析。

原冻结入口要求显式截止时间、原调度器固定1800秒，因此保留它们，新增独立入口与监控器。该版本只改变调度和允许 `stop_epoch=None` 的调用方式；底层冻结执行器本来就支持这一参数。默认 `through_pass=None` 仍逐遍执行所有工程门槛，再执行科学阶段。其source/model/runtime/UUID/候选/缓存/数值/参考隔离检查全部沿用。

九项CPU测试通过，包括精确900秒网格、有限窗口边界、无截止时间策略、原四卡和run范围、配置字节绑定、来源变更拒绝、原执行器完整续跑委派、已退出进程不发信号，以及模拟“首次忙碌→900秒后空闲→只启动一次→完成后CPU分析”的生命周期。测试未加载8B权重或执行GPU forward。`checkpoint-receipt.json`重新核验已封存遍次及1,711条检查点，重叠误差为0，剩余58,018次候选评分。

新来源通过本目录manifest固定，并在控制器、执行父进程和新spawn worker启动前验证。配置另有hash绑定。每个实验最多一个本版监控器，原执行器还有writer lock。发现run被另一执行器更改时拒绝重复启动。任何执行失败停止自动重试；已经complete/failed的run不能再评分。

真实监控目录由独立 `execution-02.json` 指向。`state.json`记录最近检查、下一次时间、启动、完成或失败；正常忙碌期间仅记日志。创建该窗口目录的 `CANCEL` 可取消监控，若已启动则只终止本监控创建的进程组。取消运行不会伪称正常checkpoint暂停，终态以run manifest为准。

这是服务器进程，应用定时工具当前不可用；不是自动唤醒聊天任务。完整运行结束后自动执行CPU分析并在磁盘保存结果，不修改旧准备/用途/人工/参考选择器，mechanism_ready仍为false。
