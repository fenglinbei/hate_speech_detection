## 1. 适用范围与依据层级

审核范围沿用冻结的 32 条 discovery，两个任务各自审核，并覆盖它们实际引用的示例、查询—示例关系及呈现的词典义项/来源命中。16 条 reserve 保留；不为修订本规则查看其正文，也不重新挑选 discovery。

规则依据按下表区分。**“原来怎样计分”与“现在怎样审核语义”是两件事。**

| 依据 | 已明确的内容 | 使用边界 |

## 2. 审核者先回答的四个问题

1. **谁在表达什么立场？** 区分当前作者、被引用者、被反驳者；记录赞同、否定、反驳、转述、反讽、自述或无法判断及其措辞依据。
2. **实际在评价谁/什么？** 分开记说话者、评价对象、引文中的对象、普通背景提及；身份出现不等于成为攻击对象。
3. **负面判断落在哪里？** 是对可指认行为的批评、对个体的辱骂，还是由个体/事件扩大到群体的贬损或排斥？可以同时记录多种表达。
4. **本句能支持到哪一步？** 保存原文片段与缺失信息。缺上文不能靠召回示例、词典、原 Gold 或模型解释补造。

先记录上述事实层，再分别给 hate 和 group 的判断。一个任务可以已解决，另一个仍未决。

## 3. hate：攻击、冒犯与立场

以下为本稿建议采用的规则；其中“保留未决”也是可执行的规则，不要求所有文本都得到二元硬标签。

| 表达类型 | 判定方法 | 不足时如何处理 |
| --- | --- | --- |
| 作者明确赞同的群体贬损、歧视、排斥或去人化攻击 | 在实际目标和作者立场明确时支持 `hate`；记录指向及贬损片段 | 目标或赞同关系不明时保留未决 |
| 普通脏词、情绪感叹、玩笑或不礼貌表达 | 词面本身不足以判 hate；若只有感叹且无攻击命题，可支持 `non-hate` | 若已构成定向辱骂但是否纳入任务 hate 无统一依据，记 `policy_ambiguous` |
| 对具体行为、事件或观点的批评 | 不从负面评价直接推出 hate；若仅批评行为、未含侮辱/身份贬损/群体泛化，可支持 `non-hate` | 夹带定向侮辱时分开记录，按个体冒犯边界处理 |
| 对个人的侮辱、威胁或人格贬损 | 先记录攻击事实；不因目标是个人就自动判 non-hate，也不直接把所有个体冒犯并入 hate | 当前任务范围不足以确定时记 `policy_ambiguous`，裁决为 `null` |
| 从个体/个别事件推广到群体 | 检查是否把负面属性赋给群体；没有“都/所有”也可能是泛化，有这些词也未必是攻击 | 分清作者在实施泛化还是反对泛化 |
| 引用、转述 | 判断作者是否认可引文；引文含攻击词不足以判作者 hate | 单纯转述且立场可辨时按作者表达判断；归属不明且影响标签时记 `context_insufficient` |
| 否定、反驳、反仇恨 | 明确否定群体贬损，且没有另行发起攻击时，支持 `non-hate` | 反驳同时攻击另一对象时分别分析，不能由开头的反对态度覆盖后续攻击 |
| 反讽、反话 | 使用文本内反差、上下句关系等证据判断实际立场，不仅凭标点、表情或攻击词 | 多种合理解释导致不同标签且缺判别语境时，记 `context_insufficient` |
| 自述、群体内自称、词语释义 | 不从身份词或污名词出现直接认定攻击；看是否实际实施/认可贬损 | 身份和使用方式无法确认时不代入作者真实身份，保留未决 |
| 机构/组织及其成员 | 分开记“批评制度/服务”“侮辱机构”“攻击其成员群体”，不互相替换 | 纯机构侮辱的 hate 范围没有统一依据时记 `policy_ambiguous` |

对个人的表达若实际攻击其群体身份，按群体/身份攻击规则判断，不因目标仅一人而排除。上述明确 hate 规则以对象属于本版本已确认的任务攻击范围为前提；对象指代明确，但这类对象是否纳入任务本身未明确时，保留 `policy_ambiguous`。临时集合或机构成员不能仅因人数多就自动套用群体攻击规则；这也不新增“仅受保护群体”的限制。

混合表达按当前作者的全部有效表达分析：若至少一处满足本规则的明确 hate，句级 hate 可判 `hate`；被明确否定的引文不能仅因包含攻击命题而计入。不存在明确 hate，且仍有可能改变句级标签的未知部分时，保持 `null`，不能默认 `non-hate`。

本稿不拟设独立的 offensive 标签，也不把 `policy_ambiguous` 当成第三个模型类别。它是人审参考不可用的原因。

## 4. group：被评价对象、类别与边界

group 审核的是文本中**实际被评价或攻击的对象所对应的数据集类别集合**，不是枚举所有出现的身份。先记录对象，再作类别映射；不从 hate 标签反推 group。

| 情形 | 建议规则 |
| --- | --- |
| 明确群体对象 | 使用 `Racism`（种族）、`Region`（地域）、`LGBTQ`（性少数）、`Sexism`（性别）、`others`（其他群体）；多个实际对象取并集 |
| 中性背景提及 | 不自动赋类；仅因为在场者有某身份、地名/性别出现在背景中，不说明该身份成为评价依据 |
| 非仇恨的群体评价 | 仍可有 group；例如对群体的评价/辩护可以为 non-hate，但不能由 non-hate 自动清空类别 |
| 被反驳的引文涉及群体 | 明确作者评价或辩护的对象；不把引文中所有身份机械并入。若原任务是否覆盖该对象仍有两种定义，记 `policy_ambiguous` |
| 个人及其身份 | 因某群体身份评价个人时，可以映射相应类别；只批评一个人的行为不自动扩大为其性别、地域等类别 |
| 仅个人目标、没有群体身份依据 | 不自动记 `others`。若原任务是否把这类个人归入 others 未明确，保留 `policy_ambiguous`，不能为方便强置 `[]` |
| 机构、企业、平台、政府 | 机构本身与其成员群体分开；不从机构所在地推出 Region，不把机构名自动归入 others。机构是否单独纳入类别不明时保留 `policy_ambiguous` |
| 地区居民与地名 | 明确按地域归属评价人群时考虑 Region；地点、行政区域或风景作为背景不自动形成该类别 |
| 国籍、民族、种族等交叠边界 | 先记原文实际指向；不能凭词面固定全部归为 Racism 或 Region。现有规则不能唯一映射时列出候选及理由，记 `policy_ambiguous` |
| others | 只在实际存在清楚的其他群体对象、且属于本任务覆盖范围时使用；不是“未知”“任意人名/机构”“嫌少一个标签”的兜底值 |
| 没有任务覆盖的目标类别 | 判断充分且没有上述类别时使用有效空集合 `[]`；目标或规则不明时使用 `null` |

类别名称只提供现有五类的对应，不补出原数据没有给出的完整 ontology。正面评价、反泛化表达中的目标遗漏，必须区分“原标注漏记”与“旧任务本来不覆盖”：前者才可记疑似错误；后者应保留政策歧义或另建已命名规则分支。

集合裁决必须完整。若可确定 Region、但另一个实际对象可能涉及 Sexism 且无法裁定，可在观察中保留确定部分及候选集合，**正式 group 裁决仍为 `null`**；不能把部分集合冒充完整答案。

## 5. 原四元组、原投影与新句级参考

原四元组为 `target / argument / targeted_group / hateful`。对合法、完整的冻结四元组，原投影保持：

```text
original_hate = "hate" if any(tuple.hateful == "hate") else "non-hate"
original_group = union(all tuple.targeted_group) - {"non-hate"}
group canonical order = Racism, Region, LGBTQ, Sexism, others
```

保留具体 group 与 `hateful=non-hate` 的合法组合；不先按 hateful 过滤，不只取第一个 tuple。缺失/非法四元组不自动投影为 non-hate 或空集合。

本轮审核形成**句级、按任务的独立覆盖层**。原四元组、原 projection、示例原答案、模型输入与原预测保持可追溯；审核不默认重写 target/argument 跨度或完整四元组。

原标签存在问题时，分别记录：原四元组本身的语义疑点、投影实现/数据适配疑点、句级目标遗漏、规则差异、缺上下文。确定性投影正确不证明源标签正确；人工不同意也不自动证明投影代码有错。

审核标签与原标签不一致，需要注明是**同规则下纠错**还是**规则口径变化**。后者不得汇报成源数据误标。审核 Gold 只用于对同一批已有预测作另一个参考下的评估；修改示例答案属于后续输入实验。

## 6. 未决、审核进度与裁决可用性

三个维度分别保存，不相互推导：

| 维度 | 值及用途 |
| --- | --- |
| 原标注审核状态 | `accepted`：认可；`suspected_error`：同一规则下有相反证据；`policy_ambiguous`：任务定义/映射冲突；`context_insufficient`：缺判别语境 |
| 参考可用性 | `resolved / unresolved`；正式裁决值为合法标签/完整集合或 `null` |
| 提交进度 | `unreviewed / draft / confirmed`；确认“未决”只表示完成记录，不表示硬标签可用 |

多个问题同时存在时保存完整理由，选一个真正阻止当前任务裁决的主状态。原 Gold 尚未揭示时，“原标注审核状态”保持未填；A 阶段只记录独立判断及其不确定原因，不能提前默认 accepted。

任何 `resolved` 裁决都必须有明确任务、文本哈希、规则版本、人工依据及裁决人。`suspected_error` 本身不生成替代标签；只有后续人工裁决解决后才可成为可用覆盖层。未解决的政策冲突和上下文不足保持 `null`。同一人完成审核与裁决可以推进，须标 `single_review`；AI 意见不得获得 human 确认身份。

若多个合理解释导向不同标签，记录候选及各自证据；若它们均导向同一任务标签，可以为该任务裁决，同时保留解释不确定性。不能让另一个未决任务阻止已经明确的任务，也不能由已决任务填充另一个任务。

## 7. 示例与词典：可靠性、适用性分开

示例作为独立文本按上述两个任务审核，先保存自身判断，再看其原答案；各任务的答案可靠性为 `accepted / disputed / unknown`。去重键至少包含来源数据身份、demo ID 和原文 SHA-256，同 ID 正文或任务答案冲突时停止合并。文本相同但 ID 不同仅记录 family，不静默合并原标注。

每个查询—示例—任务关系分别记录：

- 词义/话题关联：`direct / partial / none / unclear`，附对应片段。
- 判断规则关联：同一组取值，另附立场、目标或推理规则的对应依据。
- 是否会引入不适配词典及其具体来源边；这不等于示例整体无用。

跨话题示例可能在反泛化等判断规则上适用；同词示例可能义项不适用。示例答案可靠、示例适用于当前查询、实际造成模型变化是三个不同结论。

词典审核单位为具体义项及具体出现位置，检查：词条解释自身有无问题、该义项是否适合来源文本、是否适用于当前查询、该来源是否实际进入相关条件提示。问题标记允许多选：`valid_sense / substring_mismatch / wrong_sense / overly_narrow_definition / uncertain / not_rendered`。一条合理定义仍可能在某个位置误命中。

位置使用原文 Unicode code point 的半开区间 `[start,end)`，验证 `raw_text[start:end] == raw_surface`，另存 normalized span 与映射。仅有 entry ID 不冒充已有精确命中边；重建必须绑定冻结词典和 matcher，聚合集合不符则记 `provenance_mismatch`，不替换旧输入。

人工认为“不相关/有问题”只形成候选解释；因果效用须由后续受控输入实验检验。本阶段不因为人审意见更改资源或运行模型。

## 8. 新审核的揭示顺序与旧记录衔接

| 阶段 | 可以看到 | 保存要求 |
| --- | --- | --- |
| A：查询独立判断 | 查询、当前已冻结规则、任务名 | 保存各任务独立判断、原文证据、立场/目标和缺失信息的不可覆盖初读快照；隐藏 Gold、选样桶、资源、预测和 AI |
| B：资源审核 | 冻结词典；示例先正文、后原答案 | 示例自身初判先保存，再揭示原答案；保存标签可靠性、关系和命中审核 |
| C：原标注与轨迹 | 原查询 Gold 与模型预测；人工初判保存后可选看 AI | 记录认可/争议、裁决依据、候选解释与替代解释；保留揭示前快照 |

阶段访问约束须在服务器 API 中落实，不能只隐藏前端已收到的数据。既有工作台的初读已展示资源及示例答案，因此旧确认不能追溯认定完成本轮 A/B。旧人审只读引用正式导出快照，新增逐任务记录独立保存。

此前见过 Gold、资源、轨迹或 AI 的情况分项如实记录；未知就记未知。整轮为非盲或部分遮蔽审核，新的隐藏页面不能消除历史暴露。规则稿是 AI 辅助提案这一事实也保留。

## 9. 版本冻结、变更与重审

负责人可以确认包含“保留未决”的规则，不必先裁清每个边界。建议确认范围为：

1. 采用本稿明确的立场、目标、两任务独立、句级覆盖层及 A/B/C 顺序。
2. 对纯个体/机构冒犯、个人/机构是否映射 others、国家/民族等无法唯一归类的边界，按本稿保留 `policy_ambiguous`；不移用其他数据集的规则强裁。
3. 对仍存在会改变当前任务标签的未解决争议或关键语境缺失，可确认提交未决记录，但正式裁决保持 `null`。已完成同规则纠错裁决的 `suspected_error`，以及解释不唯一但任务标签一致的记录，可按 §6 登记为 `resolved`；后续参考依赖分析只使用已裁决任务。

确认时登记确认者、时间、完整规则文件 SHA-256 和明确接受的范围，再发布冻结版本。此稿的生成时间、Git 提交或 AI 自检通过均不是负责人确认。

冻结后的语义规则修订产生新版本，引用前版哈希并列出具体变化与受影响的审核记录 ID。改变 hate 的个体攻击范围时重审相关查询及示例的 hate；改变 group 对象/类别边界时重审相关 group；若变化适用于全体，则标记全体相关任务重审。重审以新记录 `supersedes` 关联旧记录，保留旧裁决和更正理由。

若另设“个体冒犯纳入/不纳入 hate”等规则分支，先命名、冻结适用范围，分别产生覆盖层及报告。不能看哪个分支使模型得分更高后只留下该分支。
