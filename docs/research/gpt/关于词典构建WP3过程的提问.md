# 整体规划

目前针对LexSRAG 规划了这样的实验：

P0 实验基础设施 → 阶段一来源效应 → 阶段二路径分解 → 阶段三来源冲突 → 阶段四实例归因 → 阶段五内部机制 → 阶段六因果效用修复


## P0：建立可信、可冻结的实验底座

WP0–WP2：冻结决策、数据、四字段输出协议。
WP3：构建严格 fit-only、无类别的术语理解库。
WP4–WP5：构建术语/示例检索、上下文和预算生命周期。
WP6：训练 M_LD 与 M_drop，使用 seeds 42/43/44，并仅用 calibration early stopping。
WP7–WP10：构建 placebo controls、自由生成评测、反事实 margin、确定性验证和 sealed test。

## 阶段一：验证外部证据是否真的产生推理时因果效应

在同一冻结模型上比较：

C0：无外部证据
CL：仅术语理解证据
CD：仅检索示例
CLD：两者同时使用
PL/PD：等形态 placebo controls

主要看四字段指标、Hard/Soft F1、gold-vs-counterfactual margin、双向 flip 和交互效应。

## 阶段二：区分真正的语义/结构利用与捷径

分解术语定义、示例语义、target–argument 结构、标签、格式和位置效应。

## 阶段三：研究术语证据与示例证据冲突时的仲裁

使用正确、缺失、反事实证据矩阵，分析不同字段跟随哪一来源。

## 阶段四：把错误归因到具体条目和示例

使用 leave-one-out、add-back 和 oracle，区分 retrieval、selection、utilisation、conflict 与 decoding error。

## 阶段五：内部机制定位

使用 activation patching、head/MLP knockout，定位语义利用、结构类比与标签复制通路。

## 阶段六：CUCS 修复

根据字段级 causal utility 选择、拒绝或组合上下文，同时优化准确率、捷径风险与 token 成本。

# 当前进度以及问题

目前实验正进行到WP3，其科学任务如下：


WP3 为后续 `L`（terminology evidence）条件提供正式资源。该资源需要支持
`C0/CL/CD/CLD` 因果比较，因此不能把已有的 `targeted_group` 或 `hateful` 答案提前编码进上下文。

## WP3 与后续 `M_LD / M_drop` 的关系

WP3 本身不负责训练正式 hate-speech extraction 模型。它的交付物是冻结的

`lexicon_ref.json`；WP4/WP5 再据此生成可检索、可渲染的 `L` 证据与统一 context，之后 WP6才能训练两个主要 checkpoint：

| 模型 | 训练期上下文 | 实验用途 |
|---|---|---|
| `M_LD` | 每条训练样本始终同时看到术语证据 `L` 与示例证据 `D` | 表示"始终按完整方法训练"的模型，测量一个专门适应完整上下文的模型在 C0/CL/CD/CLD 下如何响应证据删除 |
| `M_drop` | 与 `M_LD` 使用相同的 per-epoch demo 顺序随机化，但以 `p=0.5` 独立丢弃 `L` 和 `D` | 让训练覆盖四种上下文组合，降低推理时删去某类证据造成的 train–test mismatch；用于检验词典和示例效应是否依赖训练期始终存在的上下文 |

两者都会在相同 query 上评估 C0、CL、CD、CLD；主计划把 `M_drop` 作为 confirmatory，
`M_LD` 作为 secondary。它们不是用来生成或审核 WP3 词条的模型，也不会帮助 WP3 过门；
相反，它们是 WP3 发布后的下游消费者。



## 尝试与困难

### 原词典可用性不足

原人工词典自称"中文隐式仇恨俚语词表"，定义也普遍直接写成"对某群体的侮辱性用词"  ，所以即便隐藏类别，模型仍可利用：

能进入这个列表的词，大概率就是仇恨词或群体指向词。

这使得模型出现label prior  ，需要定义并构建新的外部词汇术语表，即"无类别的术语理解库"，
然而，"无类别的术语理解库"的纳入口径模糊，实际数据中，存在多种复杂情况，
比如汉语中字音/字型变化产出的"黑话"，比如 ai紫-艾滋 J生虫-寄生虫 默-黑犬 txl-同性恋，
又或者一些中性或者不带有群体贬损意味的词如 "舔狗" "龟男" "国女" "郭女" "国男" "txl"等，
新版库则同时允许中性简称、俚语、多义词、回收用法和语境依赖表达；"被收录"
只表示这个表达值得解释，不表示当前句子必然 hate，这使得需要定义一个严格的收录规范目前这方面是空白的，需要修订。

### 自动词典生成质量低

正式 data 与 train partition 冻结后，第一版 WP3 改为只从 5,165 条 fit 记录构建词典，试图
解决 dev/test 泄漏和不可重放问题，该构建以"筛选稳定损贬群体的词条"为目标。旧协议从 120,566 个原始候选中排序选择 1,000 个候选，
每个候选执行：

- 3 个 Tavily 搜索 logical slots；
- DeepSeek 的 context judge、web evidence judge、final judge 三阶段裁决；
- 保存 raw/normalized evidence、provider model、usage、配置和输入 lineage；
- 通过内容寻址 target/ref 发布。

然而，执行过程中，由于中途出现错误，运行停止，我借机筛查了一遍结果，发现质量很差：

- 前 474 条只有 39 included、435 rejected。
- n-gram/分词碎片：`女拳不`、`女拳都`、`拳在`；
- 完整句子或语法片段：`都让黑蛆喝了吧`、`属实培养奴性`；
- substring attribution：`easy girl` 的意义错误投射给 `easy`；
- 邻近类别污染：`变态 → LGBTQ`、`炼铜 → LGBTQ`；
- taxonomy 与定义矛盾：`哥布林 → Racism`；
- 通用辱骂或普通词误收：`德行`、`辣鸡`、`低能`；

由于怀疑是否初始span没抽好，于是尝试尝试双模型直接抽 span，让 Qwen3.8-27B 与 DeepSeek v4 flash 只读取原始 `content`，直接抽取 exact span。设计了240条分层抽取的case + 48重复案例用于检查一致性，结果如下：

- 两模型 exact span 集完全一致：181/240 = 75.42%；
- 其中 141/240 是双方都输出空集；
- 非空 exact span 完全一致仅 40/240；
- 59/240 存在 span 集分歧；
- has-span Cohen's κ = 0.5833；
- Qwen 判有 span 66/240，DeepSeek 判有 span 88/240；
- 两模型各自隐藏复测 exact-set 一致率均为 44/48 = 91.67%；
- JSON 与 exact-substring 结构错误为 0。

结果同时经过了全量人工检查，发现出现口径混乱旧协议问的是"候选是否属于群体损贬词"，
但是模型输出混合了多种口径，比如一些群体贬损，比如"郭女"（国女 为常用女性群体损贬）能被正常纳入，
但是一些不属于群体损贬的或者中性的也被纳入了，比如"舔狗" "基佬"，
同时，一些正常表达，比如"黑人"等也被纳入，一些隐晦但是异常的表达，比如："幕刃"（母人 平台黑化 女性群体损贬）缺出现漏检
而Stage 1 真正需要的是"这段解释是否帮助模型理解词义/语用，同时不提前给出 group/hate答案"
因此"筛选稳定损贬群体的词条"，转为"构建不提供任务答案、只帮助理解词义和语用的category-free 术语理解库"。

这一转变也带来同样的问题，究竟要用什么样的标准去构建词典？要怎么筛选原始的span？

以此针对原始span筛选过程，构建了一套新的流程，先用n-gram提取content中所有的可能词，然后在调用Qwen3.8-27B提取span，
合并后，smoke200条，由我完成人工复审。
这一轮检查发现依旧存在问题，首先是n-gram提取的候选大多数为无意义词语，一段"河南有个屁的存在感"可能出现有24个候选，完全无意义，
同时，Qwen3.8-27B提取的span也在合并过程中被淹没，单独检查发现，只看Qwen3.8-27B，其提取效果也存在不少漏检问题。
